## The verdict, stated precisely

| Question | Answer |
| --- | --- |
| Does the **pipeline** work? | **Yes** — dataset → QLoRA → adherence eval → GGUF → handoff bundle, all five legs run, all reproducible from committed configs. |
| Does the **approach** work? | **Unknown.** `dataFloor.verdict == "insufficient-data"` (protocol §5). |
| Did the approach *fail*? | **No** — nothing was tested. "Not validated" would be a claim about the method; this is a claim about the corpus. |

The protocol wrote the rule this report obeys:

> If any floor is unmet, US-006's verdict must read *"insufficient data"* — not
> "the approach did not validate". A model judgment made on 7 training records
> measures the corpus, not the method.

Every number in this document is therefore reported as a **measurement of the
pipeline**, never as evidence about small-model rule authoring. Where an
arithmetic bar happens to be satisfied, that is recorded and immediately
disqualified — see [The frozen bar, checked](#the-frozen-bar-checked).

Two properties are worth carrying forward because they were *measured*, not assumed:

- **The eval set names itself in every run.** The pipeline rebuilds the eval set
  in-process with the same seed and split as `pinakes-export-slm-eval`, so each run
  records `evalSetSha256` + `matchesFrozenEvalSet` against the committed manifest,
  and the parity CLI hard-fails on a mismatch rather than comparing two columns
  measured on two different eval sets. A run that cannot name what it scored is not
  a comparison point.
- **Reproducibility is size-dependent.** The 0.5B debug run was *not*
  byte-reproducible on MPS (adherence rates moved between identical invocations at a
  pinned seed); the 3B run was (identical rates across all three repeats, `evalLoss`
  spread 0.001); llama.cpp scoring was byte-identical to six decimals across
  independent runs. The repeat machinery is what turned that from an assumption into
  a measurement — keep it.

### Reading the quantization impact honestly

- **`evalLoss` is the only metric with the resolution to show the quantization.**
  It rose ~+0.20 nats on both arms (grounded 2.464 → 2.674, ungrounded 2.437 →
  2.626). That is Q4_K_M's real, visible cost, and it is consistent across arms —
  the sign of a genuine effect rather than a coin flip.
- **The rate movements are single prompts flipping, not findings.** The ungrounded
  arm's `fullyValid` +0.5 and the grounded arm's `reachabilityCharitable` +1.0 are
  one prompt each. Quantization does not make a model better; do not carry either
  forward.
- **Verdict on acceptability:** *provisionally acceptable for the deployment leg,
  unproven for production.* A ~0.2-nat loss rise with no rate degradation is the
  profile of a healthy Q4_K_M conversion, and it matches the quant Insimul already
  deploys. The frozen ≤2pp budget was met at 0.0pp, but at n = 2 that check has
  almost no power — it must be re-run at the floor before it means anything.

## The ablation — did tuning internalise the vocabulary?

Fine-tuned weights on the grounded prompt **minus** the same weights on the
vocabulary-stripped prompt (protocol §1; the strip is derived by
`slm_pilot.strip_grounding_block`, not hand-written). Deliberately *not* part of
the success bar.

| Metric | grounded − ungrounded |
| --- | ---: |
| `parseRate` | −0.500 |
| `schemaValidity` | **+1.000** |
| `referentialIntegrity` | +0.000 |
| `fullyValid` | **+1.000** |
| `reachabilityStrict` | +1.000 |
| `evalLoss` | +0.024 |

**The measurement:** with the grounding block, the tuned model produced
schema-valid, fully-valid rules; without it, neither. **The caveat:** that is one
prompt per cell — the maximum possible effect size at n = 2, which is exactly what
you would also see from noise.

The interesting part is the *disagreement between the two kinds of metric*.
`evalLoss` barely moved (+0.024, versus a 0.001 run-to-run spread — resolvable, but
tiny), while the adherence rates moved maximally. Teacher-forced loss on the
reference completion is nearly independent of whether the vocabulary block is
present; free generation is not. That is the signature of the grounding block
supplying vocabulary **at generation time** rather than the LoRA having absorbed
it — which is the hypothesis the ablation was built to test, pointing the way it
points at every observation available. It is one observation.

**Provisional reading: the grounding block is doing the work.** See the
grounding-block decision below.

## The decisions this skeleton deferred

The PRD deliberately guessed these and told US-006 to draft them from measurements.
Each below is stated as a **recommendation with its evidence class**, so a future
reader can see which are grounded and which are still judgement.

### 1. Model size — **change the baseline to `Qwen2.5-1.5B-Instruct`**

*Evidence class: licensing fact (hard) + measured absence of a capacity signal.*

The pilot picked `Qwen2.5-3B-Instruct` to match Insimul's already-deployed GGUF,
which was **right for proving the deployment leg and wrong for shipping**:
`Qwen/Qwen2.5-3B-Instruct` is `license: other` / `license_name: qwen-research` —
the Qwen Research License, §2(a) "FOR NON-COMMERCIAL PURPOSES ONLY" — and a
LoRA-tuned, merged, quantized derivative inherits those terms. Most of the Qwen2.5
family is Apache-2.0; **3B and 72B are the exceptions.** `Qwen2.5-1.5B-Instruct`
**is** Apache-2.0 (verified against the model card, 2026-07-22).

Nothing measured here argues for or against 3B on quality grounds — with 7 training
records, model *capacity* was never the binding constraint. So the decision should
be made on the axes that do have evidence: license, and the fact that the
deployment leg is proven for any GGUF in this family.

- **Recommend:** production PRD baselines on `Qwen2.5-1.5B-Instruct` (Apache-2.0),
  with 3B retained as a research-only comparison arm that never ships.
- **Note for Insimul:** the obligation already exists on their side —
  `scripts/setup-local-ai.sh` downloads `Qwen2.5-3B-Instruct-GGUF` today. Shipping
  a *fine-tuned derivative* in a commercial product is the distribution the research
  license does not cover. This is a decision input, not a legal opinion.

### 2. Dataset mix — **rule-SFT stays primary; set the mix from a sweep, not now**

*Evidence class: design argument + measured volumes. No mix was tested.*

Rule authoring earned its place as the primary task for a reason that survives the
data floor: it has an **objective referee** (the tier-4 harness scores a generated
rule against its world with no reference answer). Lore QA has weaker supervision;
dialogue has none of this kind.

- **Recommend:** keep rule-SFT as the primary objective. Add lore-consistency QA as
  a secondary at a *small* proportion (~20–30%) once it exists at scale, and treat
  the exact ratio as a **one-axis sweep in the production PRD**, not a number to
  guess again here.
- **Dialogue is blocked, not deprioritised:** grounded NPC dialogue needs Insimul's
  persistence fixes (`pinakes-bridge` US-LB4 — grammar-correction triples, CEFR
  joins, per-turn KB-state hash) before the turns→chat transform becomes an
  exporter. Do not put it in the first production wave.

### 3. Preference pairs / DPO — **no DPO in the first production wave**

*Evidence class: provenance of the negatives (hard) + volume.*

All 14 preference pairs today are **corruption-sampled**: a validated rule
deliberately damaged, kept only when the tier-4 validator confirms the corruption
introduced a defect the original did not have. They are not model-generated and not
drawn from real rejection sampling.

The problem is what that teaches. A DPO stage over corruption negatives optimises
the model away from failure modes **the deterministic validator already catches**,
which is the cheapest possible thing to fix and the least valuable. The negatives
worth learning from are the ones a real model actually produces and a real validator
actually rejects.

- **Recommend:** SFT only in the first production wave. Revisit DPO once Insimul
  emits a rejection-sampling `rules.jsonl` at multi-world scale (the Insimul bridge spec
  §5.1) — that exhaust *is* the preference dataset, and it arrives as a by-product of
  the corpus work that has to happen anyway.

### 4. Grounding block — **keep it in the prompt**

*Evidence class: one ablation observation (weak) + a cost argument (solid).*

The ablation points at "the grounding block is doing the work" (§ above), but at
n = 2 that is one prompt per cell. What makes the recommendation safe anyway is
asymmetry of cost: the block is a few hundred tokens in a 4096-token context, so
keeping it costs almost nothing, while dropping it on this evidence risks the
task's entire vocabulary signal.

- **Recommend:** the production prompt keeps the grounding block. `grounded` stays
  the `productionArm` in the prompt contract, as US-004 froze it.
- **Re-run the ablation at the floor** (≥ 100 eval prompts, ≥ 2 held-out worlds).
  If the gap collapses there, shrinking the block is a real context saving for
  Insimul — that is the one result worth revisiting this decision for.

### 5. What the Insimul-side in-game evaluation PRD needs

*Evidence class: read directly out of the receiving codebase (US-005), cited by
file and symbol.*

**Four runtime gaps must close before any in-game number means anything** — full
detail in [`docs/slm-insimul-runbook.md`](slm-insimul-runbook.md):

1. `LocalAIProvider.generate` concatenates the system prompt onto the user prompt
   and re-renders it through node-llama-cpp's auto-detected chat wrapper — **the
   measured prompt string cannot currently be sent.** Every adherence number in this
   report describes a string Insimul does not yet transmit.
2. Decoding defaults (0.7 / 2048 tokens, no top-k, no stop set) are not the
   contract's greedy settings, under which every number here was measured.
3. `getAIConfig().local.modelName` defaults to `phi-4-mini-q4`, which
   `setup-local-ai.sh` never downloads.
4. Rule generation calls Gemini directly (`server/services/gemini-ai.ts`) rather
   than resolving a provider through `getAIProvider()`, so `AI_PROVIDER=local` never
   reaches it — the bundled model would load and never be asked to author a rule.

Beyond the gaps, that PRD needs: **`systems.actions` with Prolog `content`** in
Bridge-2 exports (or reachability stays at its floor), an **acceptance-rate
comparison against Gemini** through the same validator gate on the same worlds, and
the in-game checklist already written in the runbook. It is an **Insimul-side** PRD;
this pilot deliberately modified no Insimul repo file.

## Recommendation

**Do NOT draft the full Phase-D production PRD yet. Draft a Phase-C corpus PRD
instead, and re-run this pilot unchanged when it lands.**

The reasoning is the pilot's own finding turned around: the pipeline is the part
that is done, and the corpus is the part that gates everything. Writing a production
training PRD today would mean guessing volumes, mix and thresholds a second time —
exactly the failure mode the skeleton's "record actuals rather than gate on guessed
numbers" discipline was built to avoid. And because the whole pilot costs about four
minutes and $0.00, the re-run is close to free: **the re-run is the go/no-go**, not
a new document.

**Prerequisites, in dependency order:**

1. **Corpus (Insimul, Phase C).** Converted worlds at scale — enough for
   `ruleSftTrain ≥ 500` / `ruleSftTrainAccepted ≥ 200` / `evalPrompts ≥ 100` /
   `evalWorlds ≥ 2`. Ship `systems.actions` with Prolog `content` alongside them.
2. **Rejection-sampling exhaust (Insimul).** A real `rules.jsonl` of accepted +
   rejected candidates; this unblocks the DPO question as a by-product.
3. **Fill the two empty comparison points (pinakes, cheap).**
   `pinakes-train-slm --gemini` with a `GEMINI_API_KEY` fills `grounded-gemini` —
   without it the *primary* bar is structurally unevaluable. Point the VESPACE
   harness at the frozen eval set for `deterministic-translator-floor`.
4. **Swap the baseline to `Qwen2.5-1.5B-Instruct`** before any run whose output is
   intended to ship (decision 1).
5. **Close the four Insimul runtime gaps** (decision 5) — an Insimul-side PRD, and a
   prerequisite for in-game evaluation, not for the re-run.

**Then re-run `slm-pilot` US-003 → US-005 unchanged.** The protocol, configs,
harness and bundle exist and are gated; the re-run's comparison table against the
*same frozen bar* is the real go/no-go for a production PRD. If the primary bar is
met there, draft it; if not, the pilot will finally have earned the right to say
"the approach did not validate", and the report should say which lever (more data,
bigger model, DPO) the numbers point at.

**One bar may be revised, and only in this direction:** protocol §5 froze the bar
before training and forbade retroactive rewriting. US-006 may *propose* a different
bar for the production PRD. The proposal: bar 3's ≤2pp quantization budget should be
re-derived at n ≥ 100 rather than inherited, because at n = 2 it was never a test.
Bars 1 and 2 should carry over unchanged — they were never given a chance to fail.

## Corrections and caveats

- **Correction to US-001 and US-003: the VESPACE harness is present.** It lives at
  `insimul-server/server/__tests__/vespace-rule-generation-e2e/` (23 files including
  `insimul-reachability-analyzer.ts`, `vocabulary-grounding.ts`, `metrics.ts`). The
  earlier stories looked in `insimul-platform` — the wrong repo of the two — and
  recorded `deterministic-translator-floor` as unreachable on that basis. The
  comparison point is fillable and should be filled on the re-run.
- **The primary bar was never evaluable**, because `grounded-gemini` was never
  measured. `gap_closure` returns `null` by construction rather than estimating a
  denominator it does not have. That is a caveat on the whole report, not a footnote.
- **Absolute reachability numbers are near-meaningless today** — the producer-side
  `systems.actions` gap (the Insimul bridge spec §5.2). Compare *spreads between
  comparison points on the identical eval set*; never quote an absolute rate as a
  grade.
- **The base model and the shipped GGUF are non-commercial** (Qwen Research
  License). See decision 1 and `ml/models/slm-pilot/LICENSE-NOTES.md` in the bundle.
- **The datasets and the tuned model are proprietary / synthetic tier.** DVC only,
  never git, never an open-data release, on either side of the bridge.
- **The 0.5B debug run is not byte-reproducible on MPS.** Any future single-draw
  0.5B number must be reported as a mean over repeats or from a fixed-seed CPU run.
