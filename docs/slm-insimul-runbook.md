## The environment block

`ai-config.ts` has no per-model registry — `getAIConfig().local` is built entirely from environment variables, and `modelName` resolves by the convention `models/<name>.gguf`. So *the model entry* is this:

```sh
AI_PROVIDER=local
LOCAL_MODEL_PATH=<insimul>/models/slm-pilot-3b-Q4_K_M.gguf
LOCAL_MODEL_NAME=slm-pilot-3b-Q4_K_M
LOCAL_CONTEXT_SIZE=4096
LOCAL_GPU_LAYERS=auto
```

`LOCAL_CONTEXT_SIZE` is the context the parity check actually ran at; `LOCAL_GPU_LAYERS=auto` matches the provider's own default (`-1` → let node-llama-cpp decide). Generation settings at the call site:

```json
{
  "maxTokens": 96,
  "stop": [
    "<|im_end|>",
    "<|endoftext|>"
  ],
  "temperature": 0.0,
  "topK": 1,
  "topP": 1.0
}
```

## In-game evaluation checklist

1. **Load the bundle** — dvc pull ml/models, copy the GGUF into Insimul's models directory, set the environment block above, and confirm the startup log (logAIStatus) names the pilot model and the 4096-token context.
2. **Verify the artifact before trusting a score** — sha256 the GGUF against model-manifest.json → model.sha256. A re-quantized or re-downloaded file is a different model and none of the numbers in this bundle describe it.
3. **Reproduce one measured generation** — Take a prompt from rule-eval.jsonl, send it through the wired path, and check the output is a single clause terminated by a period. If it is prose, the chat wrapper is still rebuilding the prompt (gap `chat-wrapper-rebuilds-the-prompt`).
4. **Generate rules in a test world** — Author N rules per world across several worlds with AI_PROVIDER routed to the local model, keeping the vocabulary-grounding block in the user turn (the production arm).
5. **Run the validator gate** — Score every generation through Insimul's 4-layer validator (structural → schema/vocabulary → referential → persist). A generation with no clause-shaped line is a PARSE FAILURE and must be rejected, never coerced — the tier-4 parser would accept "I cannot help." as a one-atom clause.
6. **Compare acceptance rate against Gemini** — Same worlds, same prompts, same grounding block, same session: accepted / total for the local model vs the Gemini path. The VESPACE harness (insimul-server/server/__tests__/vespace-rule-generation-e2e/) already computes reachability and fireability over generated rules and is the natural place to add the local-model variant.
7. **Feed the outcome back** — Every accepted/rejected candidate is preference data: the rule-candidates store (server/db/rule-candidates-store.ts) already records outcome + sourcePrompt + validator errors, and dataset-export-service builds rules.jsonl from it. That export is what lifts pinakes's corpus off the insufficient-data floor.

Quantization budget at handoff: **within-budget** (fullyValid on the `grounded` arm, observed 0.0 pp vs the frozen ≤ 2.0 pp).

Regenerate: `cd ml && uv run pinakes-export-handoff` (`--dry-run` is the model-free smoke, `--check` re-verifies a materialised bundle against its manifest).

## Why the prompt has to be sent verbatim

Everything the pilot measured — parse rate, schema validity, referential
integrity, reachability, fireability, eval loss, and the quantization parity
delta — was measured on **one exact prompt string**, rendered by
`pinakes_ml.slm_finetune.format_inference_prompt` and frozen into
[`ml/manifests/slm-prompt-contract.json`](../ml/manifests/slm-prompt-contract.json).
The model was fine-tuned on that same template (a test asserts training text is
the inference prompt plus the assistant turn), so a different rendering is a
different, unmeasured task.

Concretely, the string is:

```
<|im_start|>system
You are Insimul's rule author. Answer with exactly one Prolog rule: a single clause terminated by a period. Output only the rule — no prose, no explanation, no code fences.<|im_end|>
<|im_start|>user
{{USER_PROMPT}}<|im_end|>
<|im_start|>assistant
```

`{{USER_PROMPT}}` is the **grounded** arm: the vocabulary-grounding block
(intrinsic predicates / action-producible predicates / entity roster) plus the
authoring instruction, exactly as `insimul_datasets.build_rule_prompt` composes
it — which is the same shape Insimul's own vocabulary-grounded Gemini prompt
uses. Keep the grounding block. The US-003 ablation measured the ungrounded arm
at 0.00 schema validity against 1.00 grounded; that is one prompt per cell and
therefore not a finding, but nothing in the pilot argues for dropping it.

`system` is a **real system turn**, not a prefix glued onto the user message. The
current provider does the latter (gap
`chat-wrapper-rebuilds-the-prompt`), which is why it is the first thing to fix.

### Reading the answer back

The contract's `response` block is the parsing rule, and it exists because the
tier-4 validator is *too* forgiving at the front door:

1. strip code fences;
2. drop everything before the first clause-shaped line (`^[a-z]\w*\s*\(`);
3. take the clause up to its terminating period.

A generation with no clause-shaped line is a **parse failure** and must be
rejected. Do not pass prose through: the tier-4 parser accepts `I cannot help.`
as a one-atom clause, so a refusal coerced into a "rule" scores as a well-formed
one. `pinakes_ml.slm_finetune.extract_rule` is the reference implementation.

Then run the generation through Insimul's existing 4-layer validator gate before
persisting it. The local model does not get a shortcut the Gemini path does not
have.

## Routing rule generation to the local model

`AI_PROVIDER=local` alone is not enough today. Rule authoring
(`server/services/gemini-ai.ts` → `generateRule` / `generateRulesBatch` /
`generateBulkRules`) calls Gemini directly rather than resolving a provider
through `getAIProvider()`, so the bundled model would load at startup and then
never be asked for a rule (gap
`rule-generation-does-not-route-through-the-provider`).

The smallest change that makes the pilot testable:

1. give the rule-authoring call site a provider seam (the factory in
   `server/services/ai/ai-provider-factory.ts` already exists and is registered
   per provider type);
2. on the local path, build the prompt from the contract's
   `inferencePromptTemplate` rather than from the Gemini prompt builder, and send
   it through a **raw-completion** call (node-llama-cpp's `LlamaCompletion`)
   with the contract's stop triggers and greedy settings;
3. leave dialogue/lore generation on whatever provider it uses today — the pilot
   trained one task, rule authoring, and has no measurement to offer about
   dialogue. Routing dialogue here would be an unmeasured claim.

`LocalAIProvider` is a singleton with a serialized request queue, so a batch of
rule generations is sequential by construction. At 4096 tokens of context and
`maxTokens: 96`, one authoring call is cheap; the grounding block is what
consumes the context, so check a long world's prompt fits before assuming.

## Verifying before trusting

The bundle ships the frozen eval set precisely so the receiving side can check
that what it loaded is what was measured:

```sh
shasum -a 256 slm-pilot-3b-Q4_K_M.gguf     # == model.sha256 in model-manifest.json
cd <pinakes>/ml && uv run pinakes-export-handoff --check
```

`--check` has two tiers. The **hash tier** rebuilds the frozen eval set from the
committed fixtures and compares it to the manifest's `evalSetSha256` — that runs
anywhere, including CI, with no DVC pull, and it is what catches "the bundle's
scores describe an eval set this repo no longer produces". The **file tier**
re-hashes every bundle file against the manifest's inventory and only runs when
`ml/models` is materialised.

To re-score the GGUF itself (rather than just verify its bytes):

```sh
cd ml && uv pip install llama-cpp-python gguf sentencepiece
uv run pinakes-export-gguf --skip-convert
```

That path is byte-reproducible — two independent runs gave identical rates and
identical `evalLoss` to six decimals — so a mismatch means the artifact or the
prompt changed, not that inference is noisy.

## Licensing

`Qwen/Qwen2.5-3B-Instruct`'s model card declares `license: other`,
`license_name: qwen-research` — the **Qwen Research License Agreement**, whose
§2(a) grants rights "FOR NON-COMMERCIAL PURPOSES ONLY" and whose §2(b) requires a
separate license from Alibaba Cloud for commercial use. This GGUF is a derivative
work (LoRA fine-tune → merge → quantize), so those terms flow through to it.

Three consequences worth being explicit about:

- **Insimul already carries this obligation.** `scripts/setup-local-ai.sh`
  downloads `Qwen2.5-3B-Instruct-GGUF` today. The pilot did not introduce the
  license; it inherited it by choosing the base model that matched Insimul's
  deployment, which was the right call for proving the deployment leg.
- **Shipping is a different act from testing.** Internal research use is what the
  license covers. A fine-tuned derivative inside a commercial build is not.
- **The escape hatch is a model-size decision, and it belongs to US-006.**
  `Qwen2.5-1.5B-Instruct` is Apache-2.0 (verified 2026-07-22); 3B and 72B are the
  family's bespoke-license exceptions. If the pilot's conclusion is "3B is the
  right size", the license question has to be answered rather than inherited.

Required notices if the model is distributed at all are in the bundle's
`LICENSE-NOTES.md` (NOTICE text, the "Built with Qwen" / "Improved using Qwen"
attribution, and the changed-files notice).

**Training data:** `synthetic` tier / `proprietary` class — Insimul's own worlds
and validated rules, converted by `pinakes_ml.insimul_datasets`. Insimul-internal
only; never an open-data release, and never committed to git on either side. No
third-party model's outputs were used as training targets.
