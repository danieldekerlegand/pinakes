# Internationalization (i18n, RTL, calendars, native scripts) — US-012

Pinakes ships a **dependency-free** i18n layer, mirroring the PWA precedent
(US-011): all the gradeable logic lives in a pure, node-vitest-testable core
under `client/src/lib/i18n/`, and a thin React layer binds it to component state
and the document root. No `react-i18next`/`i18next` runtime dependency.

## Layers

```
client/src/lib/i18n/           ← pure core (no React, node-testable)
  locales.ts      LOCALES metadata, resolveLocale(), isSupportedLocale()
  direction.ts    RTL_LANGUAGES, directionForLocale(), directionForContent()
  resources.ts    RESOURCES dictionaries (en = source of truth), TranslationKey
  translate.ts    translate(key, locale, params) + {{param}} interpolation + fallback
  calendars.ts    formatHistoricalYear() (BCE/CE), formatCalendarDate() (Intl)
  names.ts        formatEntityName() → native script + romanization, RTL-aware
  create-i18n.ts  createI18n(locale) → immutable instance; .withLocale() switches
  index.ts        barrel — import from "@/lib/i18n"

client/src/contexts/I18nContext.tsx  ← React provider/hooks (glue only)
client/src/components/LocaleSwitcher.tsx  ← header language picker
```

## Adding a UI string

1. Add the key + English value to `en` in `resources.ts` (English is the
   authoritative catalog; `TranslationKey` is derived from its keys).
2. Add the same key to every other locale dict (`ar`, `es`). A parity test in
   `i18n.test.ts` fails if any locale is missing a key.
3. Use it: `const { t } = useI18n(); t("your.key", { param: value })`.

A missing translation degrades gracefully: requested locale → English fallback →
the raw key (never throws).

## Adding a locale

1. Append a `LocaleMeta` to `LOCALES` in `locales.ts` (`code`, `englishName`,
   `endonym`, `dir`, `defaultCalendar`).
2. Add its dictionary to `RESOURCES` in `resources.ts`.
3. If it is right-to-left, its code is already covered as long as it's in
   `RTL_LANGUAGES` (`direction.ts`) — add it there if new.

## RTL

Direction is **document-wide**, not per-element: `I18nProvider` sets
`document.documentElement.dir` (and `lang`) whenever the locale changes, so the
whole layout flips for Arabic/Hebrew/Farsi/Urdu. `directionForContent(langCode)`
additionally gives the correct `dir` for a single native-script string even when
the surrounding UI is LTR (e.g. an Arabic place name in the English UI) — used by
`formatEntityName`.

## Calendars & years

- **Historical years** on the deep-time axis (e.g. `-3500`) use
  `formatHistoricalYear(year, { locale, style })` → `"3,500 BCE"` /
  `"476 CE"` with localized era labels and grouped digits. Year 0 is treated as
  1 BCE. This is the right primitive for the timelines (Intl date formatting is
  not designed for negative years millennia before the epoch).
- **Concrete dates** use `formatCalendarDate(date, { locale, calendar })`, which
  wraps `Intl.DateTimeFormat` with a pinned calendar (`gregory` / `islamic` /
  `chinese` / `hebrew` / `persian`) via the `…-u-ca-<cal>` Unicode extension.
  Falls back to Gregorian if the platform can't honor the requested calendar;
  returns `""` for an invalid `Date`. `calendarsForLocale(locale)` orders the
  offered calendars (locale default first, Gregorian always reachable).

## Native scripts + romanization

`formatEntityName({ name, native, romanization, languageCode })` returns a
consistent `{ primary, native, nativeDir, combined }` for any domain
(languages, civilizations, religions, battles, …): `primary` is the
romanized/English label, `native` is surfaced only when it differs, and
`nativeDir` carries the RTL-aware direction for the native part. Wired into the
language detail panel header; reuse it in other panels rather than hand-rolling
per-domain native-name rendering.

## Testing

`client/src/lib/i18n/i18n.test.ts` (34 tests, node env) covers locale switching
(`translate`/`createI18n().withLocale`), RTL detection/direction, BCE/CE year
formatting, and Intl calendar formatting (Islamic/Chinese/Gregorian). The React
`.tsx` glue is intentionally thin (state + `document.documentElement` writes) —
vitest runs node-only and does not include `.tsx`, so keep testable decisions in
the pure core.

> **Timezone gotcha in date tests:** construct the fixture `Date` at *midday UTC*
> (`Date.UTC(y, m, d, 12)`) so the calendar day/year is stable regardless of the
> test runner's local timezone.
